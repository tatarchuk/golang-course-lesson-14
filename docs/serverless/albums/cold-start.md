# Холодний старт: власні заміри проти опублікованих (крок 4 практичної частини, слайди 44 і 47)

Нотатка-порівняння, яку останній слайд просить принести на наступне заняття. Усі власні заміри — у VM
`DockerGoGroup` (VirtualBox, arm64, 2 vCPU, 1,8 ГБ) на Floci 2.3.0 і в `sam local`; функції на Go,
`provided.al2023`, arm64, 256 МБ, зібрані з `-ldflags="-s -w"`.

## Порівняння

- **Порядок величин збігається.** Чистий холодний старт Go-функції на Floci (≈ 140–170 мс) — того ж порядку,
  що й опубліковані числа для Go на AWS (≈ 50–150 мс), і нижче за опубліковані Node.js та Python
  (≈ 180–400 мс). Теза презентації («Go попереду») локально не спростовується.
- **Але це різні величини.** Опубліковані числа — `Init Duration` у справжній Lambda: Firecracker micro-VM,
  завантаження пакета, старт середовища й init Go. Наше «≈ 170 мс» — створення й запуск Docker-контейнера у
  VirtualBox-VM плюс рукостискання з Runtime API Floci; образ середовища вже завантажений, мережі й VPC немає,
  а частку AWS CLI віднято наближено (як різницю середніх).
- **Що переноситься:** розрив «холодний vs теплий» (≈ 140–170 мс проти ≈ 1–15 мс) і вплив розміру пакета;
  абсолютні мілісекунди — ні.

## Що зміниться в продакшені (запитання слайда 44)

- Холодний старт — це `Init Duration` у звіті CloudWatch; для бінарника Go на 2,6 МБ варто чекати порядку
  50–150 мс. Він трапляється лише на першому запиті, при масштабуванні та після простою; теплий виклик — одиниці
  мілісекунд обробника.
- До відповіді клієнтові додається затримка API Gateway і мережі, якої локально немає.
- Обсяг пам'яті впливає на CPU (слайд 36): 256 МБ — це частка vCPU, і init може бути повільнішим, ніж
  на 1769 МБ; підбирати варто за справжніми `Init Duration` і `Max Memory Used`, а не за локальними числами.
- Якщо холодний старт на критичному шляху неприйнятний, допоможе provisioned concurrency (у Floci не
  реалізована); SnapStart для Go не застосовується (слайд 15).

## Застереження «Floci ≠ AWS»

Усі локальні числа — це Docker-контейнери у VM на ноутбуці, а не Firecracker у дата-центрі AWS, і кожне
вимірювання містить старт AWS CLI. Порівнювати їх з опублікованими можна лише за порядком величин і відносним
розривом холодний/теплий; справжній холодний старт видно тільки в `Init Duration` після розгортання в AWS.
