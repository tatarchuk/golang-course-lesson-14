FINDINGS

1. internal/repository/copy_repository.go:78-82 (and the pre-existing :58-61) — Low (correctness of a security claim). `AvailabilityForAlbums` and `Availability` use GORM `.Scan(...)`, and GORM's `Scan` (gorm v1.31.2, finisher_api.go:537-562) runs the statement under `logger.Recorder`, whose `ParamsFilter` delegates to the package var `logger.RecorderParamsFilter`, which by default returns the params unchanged. So `ParameterizedQueries: true` in internal/repository/db.go:43 does NOT apply to Scan: the SQL is logged with literal bound values. The repo's own evidence confirms it: docs/web/queries-catalog.txt:15 shows `WHERE album_id IN (1,2,3,...,10)` and `status = 'available'` while the other four statements show `$1$`-style placeholders. This contradicts README.md:50 ("кожен SQL-запит потрапляє в лог (без значень)"), README.md:425 ("з плейсхолдерами (ParameterizedQueries)"), the comment at db.go:43 ("never the bound values") and cmd/bootstrap/main.go:33-34. Today the leaked values are album ids and a status constant (harmless), but any future Scan over user data would log it. Fix (one line, keeps Scan): in `repository.Open` set `logger.RecorderParamsFilter = func(_ context.Context, sql string, _ ...any) (string, []any) { return sql, nil }`. Alternative: use `.Find(&rows)` (goes through the Query callback and honours ParamsFilter). Then reword README:50/425 or keep them as they are once fixed.

2. internal/handler/web/catalog.go:63-73 with internal/app/app.go:93-95,105 vs internal/handler/web/view.go:55-71 — Low. `visitor()` renders the cookie of a deleted account as anonymous (users.Get -> ErrNotFound), but `DELETE /web/albums/{id}` only runs `RequireRole` on the token claims, so a still-valid cookie of a deleted or demoted staff/admin account can delete rows until `exp` (24 h). This is consistent with the API's staff group (stateless JWT, documented at README:320-321), but README.md:574 says the deleted account's cookie "рендериться анонімно скрізь" and README:454-456 reads as if the cookie path were anonymous-or-RequireRole everywhere; the delete route is the exception. Fix: either re-check the account in `Delete` (one `users.Get`, answer 401 like `AuthHandler.Me` does) or narrow README:574 to "на сторінці й у фрагменті" and state that the delete route trusts the token until exp.

3. internal/handler/web/auth.go:26 — Low. `r.ParseForm()` on `POST /login` accepts up to net/http's default 10 MiB form body, while the API caps bodies at 1 MiB (internal/handler/request.go:13 MaxBytesReader). The login form is also an unauthenticated endpoint that always burns one bcrypt (cost 10) per request with no rate limit (pre-existing for POST /api/v1/auth/login too). Fix: `r.Body = http.MaxBytesReader(w, r.Body, 16<<10)` before ParseForm (a 400 page on overflow); note the missing rate limit in the README as a known limitation or add a simple per-IP limiter in front of both login routes.

4. internal/handler/web/static.go:14-27 — Low. Embedded files have a zero ModTime, so `http.FileServer` sends no Last-Modified/ETag and the handler sets no Cache-Control: browsers refetch the 52 KB htmx and the stylesheet on every navigation (no heuristic caching without validators). Fix: `w.Header().Set("Cache-Control", "public, max-age=86400")` (or content-hashed file names) before `files.ServeHTTP`, plus `X-Content-Type-Options: nosniff`.

5. internal/app/app.go:100-106 / internal/handler/web/templates.go:64 — Low. The HTML responses carry no security headers: no Content-Security-Policy, X-Content-Type-Options, Referrer-Policy or X-Frame-Options/frame-ancestors. htmx is self-hosted and there is no inline script, so `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'` would work today (false-positive risk: hx-on/hx-vals "js:" would later need 'unsafe-eval'; verify in a browser). Fix: a small middleware around the web group setting these headers.

6. web/templates/partials/album_row.html:9 + internal/handler/web/catalog.go:69 — Low (UX). On 401/403/404/500 the delete route answers the JSON envelope; htmx 2's default responseHandling does not swap on 4xx/5xx, so the row stays and the user sees nothing (an expired cookie mid-session looks like a dead button). A template/storage failure on the page shows raw JSON (acknowledged in handler.go:49-50). Fix options without custom JS: send `HX-Retarget`/`HX-Reswap` headers with a small HTML error fragment from `Delete`, or the htmx `response-targets` extension; at minimum document the behaviour.
